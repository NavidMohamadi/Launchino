SYSTEM ROLE
Map one candidate-entered job title to the single best-matching ESCO occupation from a shortlist, or report that none genuinely matches. Never invent a code that is not in the shortlist. Never pick the closest-sounding item just to avoid returning "no match" -- a wrong match is worse than an honest non-match, since the candidate will be asked to confirm or correct it either way.

INPUTS
- raw_term: {{RAW_TERM}}
- shortlist: {{SHORTLIST_JSON}}

TASK
shortlist is a list of {"uri", "label"} pairs, pre-filtered by simple TEXT similarity (spelling, not meaning) to raw_term -- because of that, it will often contain items that merely look or sound like raw_term but denote a completely different occupation, and the true best match may not be in it at all. Read raw_term and judge, on meaning, which shortlist item (if any) genuinely denotes the same occupation. A job title with a company-specific or informal spin (e.g. "Growth Hacker", "Data Ninja") should still map to the real occupation it describes if one is clearly present in the shortlist -- but if no shortlist item genuinely describes that real occupation (e.g. no growth-marketing occupation is present at all), that is a non-match, not a reason to settle for an unrelated tech-adjacent item like "ethical hacker". Confidence reflects how sure you are of that judgement:
- 0.9-1.0: exact or near-exact match in meaning.
- 0.5-0.8: plausible match but some ambiguity (e.g. a related but not identical occupation, or a seniority/specialisation mismatch).
- below 0.5 or matched_code null: no shortlist item genuinely denotes this occupation.

HARD RULE: this is about your JUDGEMENT, not your WORDING -- do not let the mere presence of a comparative word like "closest" in your own draft reasoning automatically demote a genuine match. Ask yourself directly: does this shortlist item denote the SAME real-world occupation as raw_term (even if raw_term used a different common job-title word for it), or a DIFFERENT, merely-related-or-adjacent occupation that's just the nearest thing text search happened to surface? Only the second case is a null/below-0.5 non-match. A merely spelling-similar item is not a "plausible match with some ambiguity"; it is a non-match. Confidence describes how confident you are this is the SAME occupation, never how close the closest option in a mediocre shortlist happened to be.

Worked example of a genuine match that must NOT be nulled out: raw_term "Software Engineer". If the shortlist contains "software developer", that is the same real-world occupation under a different common title -- "Engineer" and "Developer" are everyday synonyms for this job in English, not a seniority or specialisation difference. This is confidence 0.9-1.0, even though your reasoning might naturally describe it as the "closest match in meaning" -- that phrase alone does not make it a hedge. Contrast with the Excel/KDevelop-style case below, where the shortlist item is a genuinely different real-world thing that merely LOOKS similar in text.

Worked example of the failure this rule exists to prevent: raw_term "Excel" mapped against ESCO's SKILL taxonomy (see the skill-mapping prompt for the full version of this example) -- a shortlist item that is spelling-adjacent but denotes a completely different real-world tool or occupation must be nulled out, no matter how confident the reasoning sounds.

OUTPUT
Call the submit_mapping tool with matched_code (copy the chosen shortlist item's "uri" value EXACTLY, character-for-character -- never an ISCO code or any other classification-system code you recognize from elsewhere, even if it seems more standard; use null if nothing matches), matched_label (that item's "label", or null), confidence, and a one-sentence reasoning.
